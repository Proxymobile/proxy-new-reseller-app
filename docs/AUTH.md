# Authentication System

## Overview

Access-code-only authentication. No email, no password, fully anonymous. Accounts are created by admins and identified by a 16-character hex code formatted as `xxxx-xxxx-xxxx-xxxx`.

## How It Works

### Account Creation (Admin Only)
1. Admin navigates to `/admin/accounts/create`
2. Enters a label (e.g. "client-47") — this is the only required field
3. System generates a cryptographically random access code via `crypto.randomBytes(8)`
4. Code is displayed once — admin copies and shares it with the customer
5. A `customers` row is auto-created for customer-role accounts

### Login
1. User visits `/login`
2. Enters their access code (auto-formatted with dashes as they type)
3. System validates: rate limit check → DB lookup → timing-safe compare → enabled check
4. On success: JWT session created, redirected to `/dashboard`
5. On failure: generic "Invalid or disabled access code" (no information leakage)

### No Self-Registration
- `/register` redirects to `/login`
- There is no public account creation endpoint
- Only admins can create accounts via `POST /api/admin/accounts`

## Security Measures

### Rate Limiting
- 5 failed attempts per access code per 15-minute window
- Tracked by SHA-256 hash of the attempted code (first 16 chars)
- Failed attempts recorded regardless of whether the code exists
- Old attempts auto-cleaned on successful login (24h TTL)

### Timing-Safe Comparison
- `crypto.timingSafeEqual` used after DB lookup
- Prevents timing-based side-channel attacks on code matching

### Session
- JWT strategy (stateless, no DB session table needed)
- Token contains: `id`, `role`, `label`, `walletRequired`, `walletChain`
- Signed with `AUTH_SECRET` environment variable

### Access Code Properties
- 16 hex characters (64 bits of entropy, ~1.8x10^19 possible codes)
- Formatted as `xxxx-xxxx-xxxx-xxxx` for readability
- Generated via `crypto.randomBytes(8).toString('hex')`
- Stored in `users.access_code` column with UNIQUE constraint
- Can be regenerated by admin (old code immediately invalidated)

### Middleware Protection
- All `/dashboard/*` and `/admin/*` routes require authentication
- Admin routes additionally checked via `isAdmin()` in layouts and API routes
- Unauthenticated users redirected to `/login`
- Already-authenticated users on `/login` redirected to `/dashboard`

## Wallet 2FA (Optional)

Accounts can optionally link a Solana or Ethereum wallet for additional verification.

### Linking Flow
1. Authenticated user calls `POST /api/wallet/challenge` with `{ chain, address }`
2. Server creates a 5-minute nonce challenge
3. User signs the challenge message with their wallet
4. User submits signature to `POST /api/wallet/verify`
5. Server verifies nonce validity, marks wallet as linked

### Challenge Security
- Nonces are 32 hex chars (`crypto.randomBytes(16)`)
- Each challenge expires after 5 minutes
- Challenges are single-use (marked `used = true` after verification)
- One wallet address can only be linked to one account
- Old/used challenges auto-cleaned on new challenge creation

## Database Tables

| Table | Purpose |
|-------|---------|
| `users` | Core accounts with `access_code`, `role`, `enabled` |
| `login_attempts` | Rate limiting (hashed code, timestamp, success flag) |
| `wallet_links` | Linked wallet addresses per user |
| `wallet_challenges` | Ephemeral signing challenges for wallet verification |
| `audit_log` | All auth mutations logged (create, toggle, regenerate, wallet link/unlink) |

## API Endpoints

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| POST | `/api/auth/[...nextauth]` | Public | NextAuth sign-in handler |
| POST | `/api/admin/accounts` | Admin | Create new account |
| PATCH | `/api/admin/accounts` | Admin | Toggle enabled, regenerate code, unlink wallet |
| GET | `/api/admin/accounts` | Admin | List all accounts |
| POST | `/api/wallet/challenge` | User | Request wallet linking challenge |
| POST | `/api/wallet/verify` | User | Submit wallet signature |

## Key Files

- `src/lib/auth.ts` — NextAuth config, authorize logic, account management functions
- `src/lib/auth.config.ts` — Middleware-compatible auth config (route protection)
- `src/middleware.ts` — Edge middleware for route guards
- `src/types/next-auth.d.ts` — Session/JWT type extensions
- `src/app/(auth)/login/page.tsx` — Login UI
- `src/app/api/admin/accounts/route.ts` — Account CRUD API
- `db/schema.sql` — All auth-related tables
